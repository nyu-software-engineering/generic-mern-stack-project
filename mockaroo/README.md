# Mockaroo setup

The shared mock API returns users, listings, rentals, conversations, reviews, and item requests. These files contain the schema formula and API handler used by Mockaroo.

## Run the app

Use the setup commands in the [root README](../README.md#development-setup). Copy `front-end/.env.example` to `front-end/.env.local`, then set `MOCKAROO_API_KEY` using the key shared privately. Restart Vite after changing it.

- Remote endpoint: `GET https://my.api.mockaroo.com/dormshare.json`
- App request: `GET /mock-api/dormshare.json`
- Authentication: Vite adds the `X-API-Key` header from the environment file.
- Response: an object with `users`, `listings`, `rentals`, `conversations`, `reviews`, and `itemRequests` arrays.
- Initial records are cached by Mockaroo for one day. Local app edits stay in memory and reset on reload.

Teammates using the existing endpoint only need the key. They do not need a Mockaroo account. Editing its saved schema requires access to the account that owns it.

## Recreate or update the saved API

1. In Mockaroo, create or edit the schema named `DormShare`.
2. Use one field named `data`, with type **Formula** and blank percentage **0**. Paste the contents of [schema-formula.rb](./schema-formula.rb) into it.
3. Set the row count to **1**, the format to **JSON**, and enable **array** and **include null values**. Save the schema.
4. Create or update the mock API with method **GET** and route **/dormshare.json**. The existing [api-handler.rb](./api-handler.rb) remains unchanged.
5. Clear the API's cached results after saving the schema; otherwise the old response will be returned for up to one day.
6. Confirm the endpoint response contains `reviews` and `itemRequests` arrays before running the updated frontend. The frontend requires all six arrays and intentionally has no hardcoded fallback.

The formula generates 8 users, 8 listings, 15 rentals, 3 conversations, 2 initial reviews, and 5 item requests. Rentals cover all seven statuses. `owner-1` is the borrower on rentals 104 (confirmed), 105 (extension requested), 113 (completed) and 115 (active), so the borrower side of extensions, cancellation and reviews can be tested. User IDs are strings (`owner-1`, `student-2` through `student-8`). Listing and rental IDs are numbers. Listing 5 belongs to `student-2`; the other listings belong to `owner-1`. Names and prices are generated by Mockaroo. Dates are relative to the day of generation.

These Ruby files configure Mockaroo. The app fetches the generated response and does not import these files as fixtures. When editing the saved configuration, update these copies in the same PR.

## Conversations

Conversations reference users and listings in the same response. Messages are ordered from oldest to newest.

| Record | Fields |
| --- | --- |
| Conversation | `id` (number), `listingId` (number), `participantIds` (two user ID strings), `messages` (array) |
| Every message | `id` (number, unique across messages), `senderId` (user ID string), `type` (`text` or `offer`), `sentAt` (ISO timestamp) |
| Text message | `text` (string) |
| Offer message | `totalPrice` (number), `startDate` and `endDate` (`YYYY-MM-DD`), `status` (`pending`, `accepted`, `declined`, or `countered`) |
| Accepted offer | `bookingId` (number, added when a booking is created) |

The samples include two pending offers: one received by `owner-1` as a borrower and one as an owner. A third conversation contains text messages only. Offer dates are in the future when generated. Message timestamps use UTC.

## Reviews

Reviews belong to completed rentals. The seed contains two reviews received by `owner-1`, based on bookings `106` and `113`, with reviewer IDs derived from the corresponding rental participant. The review schema includes `id`, `bookingId`, `reviewerId`, `reviewedUserId`, `communicationRating`, `itemCareRating`, `overallRating`, `comment`, and `createdAt`.

New review submissions are added to the shared frontend in-memory store, so they survive navigation but reset on a full reload. No backend write endpoint is implemented for Sprint 1.

## Item requests

An item request is something a student needs that is not listed yet. Other students respond in chat by offering one of their published listings for the requested dates. Field names match Quick Borrow requests (`itemName`, `neededBy`, `approximateArea`, `details`, `createdAt`) so the shared requests board can show both.

| Field | Type |
| --- | --- |
| `id` | number |
| `requesterId` | user ID string |
| `itemName` | string, what the student needs |
| `neededBy`, `neededUntil` | `YYYY-MM-DD` |
| `approximateArea` | string |
| `targetPrice` | number or `null` (optional) |
| `details` | string (may be empty) |
| `status` | `open` or `closed` |
| `responses` | array of `{ responderId, conversationId, messageIds }`, where `messageIds` are the messages the responder sent for this request; empty when generated |
| `createdAt` | ISO timestamp |

The seed contains four open requests from other students and one from `owner-1`, so both the board and "My requests" have data. One request has no target price. Request dates are in the future when generated. New requests and responses are added to the shared frontend in-memory store and reset on a full reload.
