## URL and wrapper rules

- `MockData` is a pathless parent for 21 routes, including Browse, listings, bookings, profile, inbox, reports, reviews, notifications, and requests. It must finish `loadMockData()` before any child renders. Its shared loading and retryable error screens need the same design coverage as the pages. `SavedItemsProvider` is another pathless wrapper for only `/browse`, `/browse/:id`, and `/renter-dashboard`. It lets its children render while saved items load. Neither wrapper adds a URL. Sources: `front-end/src/App.jsx`, `front-end/src/components/MockData.jsx`, `front-end/src/context/SavedItemsProvider.jsx`.
- `/inbox?conversation=<id>` selects a child view. Offer entry is an overlay on that view, with no extra URL. `/requests?new` selects create, `/requests?request=<id>` selects detail, and `new` wins if both are present. `/listings/:listingId/request?start=YYYY-MM-DD&end=YYYY-MM-DD` prefills valid dates. `/report?rentalId=<id>`, `?conversationId=<id>`, or `?listingId=<id>` supplies report context. These are query states of existing routes. Sources: `front-end/src/pages/chat/Inbox.jsx`, `front-end/src/pages/requests/ItemRequests.jsx`, `front-end/src/pages/booking/Booking.jsx`, `front-end/src/pages/reporting/Report.jsx`.
- There is no wildcard client route or app-wide auth guard. Only verify, setup, and profile have render-time auth redirects. Navbar hides its action links when signed out, but most direct URLs still render. Do not assume a protected shell already exists. Sources: `front-end/src/App.jsx`, `front-end/src/components/Navbar.jsx`, `front-end/src/pages/auth/VerifyEmail.jsx`, `front-end/src/pages/auth/SetupProfile.jsx`, `front-end/src/pages/auth/Profile.jsx`.

## API, cache, and async boundaries

- **Shared transport:** `front-end/src/services/api.js` calls same-origin `/api`, uses a 15-second timeout, JSON bodies, and `ApiError(message, status, errors)`. It distinguishes unreachable backend, server errors, and unreadable success JSON. `front-end/vite.config.js` proxies `/api` to port 3001. `back-end/app.js` serves built frontend paths and listing image files. Keep these contracts stable during a visual redesign.
- **Bootstrap cache:** `front-end/src/services/mockDataService.js` loads `/api/mock-data` once per module lifetime, validates the payload, and caches users, listings, rentals, conversations, reviews, and requests. Failed loads clear the pending promise for retry. Cache writes have no subscription mechanism. Pages commonly snapshot cache data into local state, so the redesign must not assume live updates or refresh persistence.
- **Identity split:** `front-end/src/context/AuthProvider.jsx` keeps account identity and profiles in React memory. Login does not check passwords. Verification is simulated. Service identity is the constant `owner-1` in `front-end/src/services/mockDataService.js`. The server also sets `owner-1` in `back-end/middleware/currentUser.js`. This explains the profile's demo reputation link. Real authentication and API integration are separate work, not a visual-state promise.
- **Discovery and listing API:** `services/publicListings.js` calls `GET /listings` and `GET /listings/:id`. Browse delays text searches by 200ms. Its AbortController prevents stale rendering and cache writes, but the signal is not passed through to the network helper. Listing detail refresh populates cache for booking/report readers. `services/listings.js` uses owner GET, POST, PUT, and status PATCH, then caches results. A full owner list refresh replaces that owner's cached listings. Do not remove cache writes while restyling forms.
- **Dashboards and saves:** `services/ownerDashboard.js` queries `/owner/dashboard` with search/status. `services/renterDashboard.js` gets `/rentals/mine` and updates cache. `services/savedItems.js` uses GET, POST, and DELETE `/saved-items`. The saved provider deduplicates per-listing mutations, then updates its own shared list. Rental and save sections need independent failures and retries. Source roots: `front-end/src/`, with contracts in `back-end/routes/ownerDashboard.js` and `back-end/routes/renterDashboard.js`.
- **Booking API and local exceptions:** `front-end/src/services/bookingsApi.js` calls booking create/detail/request-list/status, extension create/respond/list, and cancel endpoints. Returned bookings update cache. Chat-created bookings use ids from `1_000_000_001`. Chat and handoff mark bookings local-only. The API service then reads or mutates those local records without overwriting them with server data. `services/bookings.js` derives overdue from active/extension status and return date. Preserve role/status gates and local-only handling. Sources: `front-end/src/services/bookingsApi.js`, `front-end/src/services/bookings.js`, `front-end/src/pages/booking/useBooking.js`, `back-end/routes/bookings.js`.
- **Messages and requests remain local in the UI:** `front-end/src/services/chat.js` handles message, offer, counter, accept, decline, and conversation creation synchronously. `services/itemRequests.js` creates/closes requests and records response message ids so the board can show the correct latest reply. `services/requestsBoard.js` merges these with Quick Borrow. Backend conversation endpoints exist in `back-end/routes/conversations.js`, but the frontend chat service does not call them. Avoid drawing network delivery or server persistence guarantees into the redesign.
- **Storage exceptions:** `front-end/src/services/quickBorrow.js` combines bootstrap data with requests in localStorage. It handles read/parse errors but not failed writes. `/quick-borrow` is outside `MockData`, so a direct visit can submit before shared data loads. The board will load shared data later. `services/notifications.js` derives notifications from cached rentals/messages/reviews. It persists read ids in localStorage with an in-memory fallback. Neither feature has a server subscription.
- **Trust boundaries:** `front-end/src/services/reviews.js` validates and saves reviews in memory. Reports and rules use real API requests in `services/reports.js`. Report subject display resolves cached records. The server validates rental/conversation participation. The optional image input sends only `imageName`, not file content. `ReportSubmitted` fetches a receipt but resolves its subject locally. Preserve privacy and validation copy without presenting file upload or moderation actions that do not exist. Contracts: `back-end/routes/reports.js`.

Frontend service paths without a full prefix in this section are relative to `front-end/src/`. Stored enums are defined in `shared/options.mjs`: three listing states, seven rental states, four offer states, two item request states, and four report reasons. Overdue is derived rather than stored.

## Handoff for implementation and browser QA

Each issue should cover the listed child states as well as its route count. Shared load and save errors belong in #142's reusable patterns. Feature issues must keep field values after recoverable errors, protect pending actions, preserve role/status conditions, and give clear routes back from missing records.

Browser QA should cover every route at phone and desktop sizes, plus direct deep links and query states. Check 320 CSS pixels, enlarged text, keyboard navigation, focus after modal close, long names and messages, empty data, timeout/retry, status changes, and reload behavior at the API/cache boundary. These checks are outstanding for issue #148. This report does not claim they passed.
