## Security source

OWASP recommends equal confirmations and comparable response timing for known and unknown accounts. It calls for side-channel delivery, random secret tokens, secure storage, expiry, single use, and abuse controls. It advises the same password policy as the rest of the app, password confirmation, normal login after reset, session invalidation, and a password-change notice. Reset links need a trusted origin, HTTPS, and referrer protection. Forgotten-password requests must not lock the account. These are external recommendations, not approved project settings. See the official [Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), sections “Forgot Password Request,” “User Resets Password,” “URL Tokens,” and “Account Lockout.”

## Minimal contract proposal, not approved

Keep recovery inside the existing Express account system. Add only recovery metadata alongside `app.locals.auth`; keep secrets out of shared users and `/api/mock-data`. Do not introduce a framework, database, external queue, JWT reset scheme, or dependency before a concrete need is agreed.

| Endpoint | Proposed request | Proposed result |
| --- | --- | --- |
| `POST /api/auth/forgot-password` | `{ email }`, using existing normalization | For every valid email submission, `202 { message: "If an account exists for this email, password reset instructions will be sent." }`. Unknown accounts and suppressed per-email repeats get the identical result. No user, reset token, reset URL, verification code, or delivery status appears in the response. |
| `POST /api/auth/reset-password` | `{ token, password }` | `200 { message: "Password updated. Sign in with your new password." }`. Invalid, expired, superseded, and used tokens share `400 { error: "This reset link is invalid or has expired." }`. Invalid password input uses 400 with the existing 8-128 rule. No session is created. |

Reject malformed input before account lookup. A 429 for an IP limit must apply independently of whether an account exists. Per-email suppression should count normalized unknown addresses too and retain the generic confirmation. A service-wide configuration outage can return the same safe 503 for all valid submissions. A recipient-specific delivery failure must not change the public response or reveal account existence. Exact messages, status choices, limits, and timeout behavior need agreement with #94.

Generate a separate 32-byte random reset secret. Store only its digest with `{ userId, email, expiresAt }` in process memory. It must identify both an existing credential entry and its shared user. A mock user without registered credentials is not a recoverable account. Proposed latest-link behavior is to supersede prior tokens only when a new delivery attempt succeeds. Expire and remove stale records, and bound limiter metadata. Preserve account verification state during reset. An unverified account remains unable to log in until the existing verification step succeeds.

On reset, validate the password before consuming a valid token. Use the signup hash method with a fresh salt. Claim the token, replace credentials, and invalidate all reset tokens and sessions for that user in one synchronous critical section after any required data load. No delivery await belongs inside this section. Concurrent submissions must have one winner. Rejected attempts must leave credentials and other users' sessions intact. These are proposed behavior and test requirements for the current single-process design.

Apply bounded limits to request volume by IP and normalized email, plus reset attempts by IP and token digest. Avoid scrypt work on malformed reset inputs. The owner must approve expiry, retry spacing, window lengths, thresholds, and trusted proxy handling. No numeric settings have been approved. The existing signup password range is a compatibility baseline, not a claim that production password security is complete. A policy change should update signup and reset together.

Use a configured application origin, never a submitted origin or request Host. A possible link is `/reset-password#token=<secret>`. The client would capture the fragment, remove it from the address bar, and send the secret only in the reset POST body. MDN confirms that [URI fragments are not sent with the HTTP request](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Fragment). Using a fragment to avoid initial request URL logs is a design inference. It still needs browser tests, `no-referrer`, no token storage, and no token capture by analytics or error reports. Provider mail payloads must not be logged. Local HTTP may be allowed only for an explicit local test origin.

## Delivery injection and repeatable local proof

Proposed extension: `createApp({ store, recovery: { deliver, now, publicOrigin, policy } })`. Existing callers must continue to work. The injected `deliver(message)` returns a promise. Messages have `kind: 'password-reset'`, registered recipient `to`, `resetUrl`, and `expiresAt`; a separate `kind: 'password-changed'` message contains no password or reset secret. A production adapter must use an approved mail provider. Tests use a private in-process capture adapter that can resolve or reject deterministically.

The HTTP response must not wait on an account-specific provider round trip. Schedule bounded delivery work with explicit error handling and a private completion hook for tests. This is not a durable queue. Raw tokens may exist temporarily in that private delivery payload, but never in an HTTP response, public outbox endpoint, normal application log, or persisted shared user. On reset-mail failure, invalidate that failed attempt and retain any earlier valid link according to the agreed supersession rule. A password-change notice failure cannot roll back a completed password change. Record only a safe failure category. The exact scheduling and supersession algorithm must be reviewed for overlapping requests.

A local integration test can start the actual Express app with fixture data and this capture adapter. It signs up and verifies an account, requests recovery over HTTP, waits through the private completion hook, and reads the link from the adapter's captured message. It then submits a new password over HTTP and checks the normal login route. It needs neither an inbox nor a public token retrieval route. Inject `now()` to test expiry without waiting. The existing [account tests](../../back-end/test/accounts.test.js) and [test server helper](../../back-end/test/helpers/server.js) provide the test harness. A capture adapter proves application delivery wiring. A separate provider sandbox check is needed to prove the selected provider actually accepts mail.
